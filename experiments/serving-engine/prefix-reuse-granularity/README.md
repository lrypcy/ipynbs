# prefix_reuse_granularity：前缀复用粒度的代价

对应文章：[《推理引擎（01）：架构分歧的根 —— 三条独立的设计路线》](https://lrypcy.github.io/2026/10/18/serving-01-architecture-divergence/)
（`lrypcy.github.io` 推理服务分类，serving 系列第 1 篇）。

## 这份脚本回答什么

vLLM 的 KV 缓存按 **16 token 定长块**组织，SGLang 用 **radix tree 按 token 级**匹配公共前缀。
流传的说法是「token 粒度让 SGLang 的前缀复用显著更高」。这份脚本把这句话摆到数字上：
**粒度差异到底值多少 token**。

用**纯 numpy / CPU** 跑了三组，每组都做「解析真值 ↔ 数值反算」自校验。

## 如何运行

```bash
python3 run.py              # 跑全部三组，打印表格
python3 run.py --selftest   # 只跑断言（静默），适合挂 CI
python3 run.py 1 3          # 只跑第 1、3 组
```

依赖只有 numpy，固定 `seed = 20261017`，逐位可复现。

## 三组检查与结论

| # | 检查内容 | 结论 |
| --- | ---: | --- |
| 1 | 对齐损失 $$L \bmod B$$ 的闭式与蒙特卡洛对拍（$$B = 16$$） | 解析真值 7.500000，400k 样本蒙特卡洛 7.503692。**损失与 $$L$$ 的绝对大小无关**，上限恒为 $$B-1 = 15$$ token |
| 2 | 四种负载分布下的加权复用率 | 均匀前缀 99.2894%、共享长系统提示 99.3166%、多轮对话 99.3761%、**短对话（$$E[L]=71.95$$）89.6613%**。损失率随前缀变短单调放大 |
| 3 | 定长块的内部碎片 | 平均碎片率 **1.2602%**，同容量下驻留请求数是 token 级的 **0.9930 倍** |

**一句话结论**：块对齐是一笔**绝对额不超过 15 token 的固定税，不是比例税**。
在长前缀负载上它不到 1%，只有在短对话（$$E[L]$$ 几十 token）上才放大到 10%。
所以「16 对齐让 vLLM 的前缀复用大幅落后」这个说法，只在短前缀负载上成立；
在典型的长系统提示 / 多轮对话负载上，粒度差本身不是决定因素。

完整输出见 [`results/summary.md`](results/summary.md)。

## 哪些结论是这份脚本**没有**主张的

- **不主张任何吞吐 / 延迟数字**。粒度只是三个设计维度中的一个，真正的端到端差距
  还取决于淘汰策略、调度重叠、路由，以及负载里的前缀复用率本身。
- 组 3 的碎片率与驻留比是**结构量**，只主张「分配粒度 ≠ 复用粒度就会产生碎片」这个机制；
  具体倍数由真实请求长度分布决定，不主张实测显存数字。
- 组 2 的四种负载是**构造分布**（用来展示损失率随 $$E[L]$$ 的变化趋势），
  不是从真实线上流量采样出来的。
- 脚本全程没有模拟真实的缓存淘汰过程，因此**不回答**「换成 radix tree 命中率会提升多少」。
